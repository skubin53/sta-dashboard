## What that fix cost, and the lesson

Changing body copy is NOT like changing an image. It needs POST-new + archive-old, and
I handled it badly:

1. First I re-tested whether `PUT /blogs/posts/{id}` persists `rawHTML`. It does not.
   It returned 200 and echoed back the OLD 16,443-char body against the 16,934 we sent.
   The standing note is confirmed, not superstition. Worth knowing the PUT also 422s
   without `locationId` and `blogId`, which is probably why it once looked like a no-op.
2. Trying to archive the old post, I sent `status: ARCHIVED`. There is no such status.
   The API accepted `status: DRAFT` instead and **took the live post offline**. The URL
   404'd for several minutes. That was my error and it was avoidable.
3. Recovery: POST the new body, PUT the OLD post onto a throwaway slug
   (`is-avocado-oil-fake-superseded-20260731`, DRAFT), then PUT the NEW post onto the
   clean slug with status PUBLISHED. Back to 200.

**GHL blog facts now established by test, not assumption:**

| Thing | Truth |
|---|---|
| `PUT` with `rawHTML` | silently ignored, returns 200, body unchanged |
| `PUT` with `urlSlug` / `status` | works, persists |
| `PUT` without `locationId`+`blogId` | 422 |
| archive control | boolean field `archived`, NOT `status: ARCHIVED` |
| `status: ARCHIVED` | invalid, and setting `DRAFT` UNPUBLISHES a live post |
| freeing a slug | move the old post to a throwaway slug, then PUT the clean slug onto the new post |
| swapping an image only | overwrite the same repo path, no republish needed |

**Order of operations for any future body edit: POST the new post FIRST, confirm it
exists, and only then move the old one off the slug. Never take the live one down first.**
